# 京准通「推广计划」列表里的「趋势」元素 —— 数据评估

> 结论先说：**这个趋势弹层是「分时（每小时）曲线」，日粒度你已经有了，真正的新增价值是分时。**
> 它能直接支撑「分时折扣 / dayparting」——按小时把钱从低 ROI 时段挪到高 ROI 时段。

---

## 1. 那个元素是什么

列表行里的

```html
<div clstag="h|keycount|reduced_list_...|110" class="pointer reduced-blue">
  <span class="reduced-blue">趋势</span>
</div>
```

是**计划行的「趋势」入口**。点开后页面渲染出一个 `div#planContainer.trendPic-container`
（canvas 图表，横轴 `00:00 / 04:00 / 08:00 / 12:00 / 16:00 / 20:00`），即**该计划的分时曲线**。

> 注意：列表里 `clstag` 含 `reduced_list` 的元素有 39 个（筛选按钮、重置列宽等都用同一前缀），
> 只能按**可见文本「趋势」**定位，不能只按 clstag 前缀选。

## 2. 背后的接口

点开「趋势」时会打两组请求（都在 `https://atoms-api.jd.com`，靠页面 Cookie + 首次访问
`jzt.jd.com/msa/` 建立的 SSO 上下文鉴权）：

| 用途 | 接口 | 关键参数 |
|---|---|---|
| 该计划**当日汇总** | `POST /reweb/common/index/indicator` | `campaignIds:[id]`, `startDay/endDay` |
| 该计划**分时曲线** | `POST /reweb/common/index/material/trendchart` | `campaignIds:[id]`, **`granularity:4`** |

账号级（非按计划）用另一个路径：`POST /reweb/common/index/trendchart`。

公共参数：

```json
{"startDay":"2026-10-11 00:00:00","endDay":"2026-10-11 23:59:59",
 "businessType":-4,"granularity":1,"isMsa":1,"type":1,
 "copyWriting":"广告点击15天内累计的成交订单","clickOrOrderDay":15,
 "clickOrOrderCaliber":0,"orderStatusCategory":1,"deliverySystemType":0}
```

`businessType:-4` = 京准通整体；`clickOrOrderDay:15` = 点击后 15 天归因（与现有抓取口径一致）。

## 3. 能力矩阵（实测）

`granularity` 语义与取数边界（`data/explore/trend_probe3.json`）：

| granularity | 时间粒度 | 返回的 date 形如 |
|---|---|---|
| 1 | **天** | `20261011` |
| 2 | **周** | `2026W41` |
| 3 | **月** | `202610` |
| 4 | **小时** | `20261011000000~20261011005959` |

边界：

* **小时粒度只在单日内生效**。区间 >1 天时 `granularity:4` 会**静默降级为按天**（实测 30 天区间只回 30 行），不会报错。
* `material/trendchart` **必须传 `campaignIds`**，不传返回空。
* **多个 `campaignIds` 是「求和」**，不返回逐计划明细。要逐计划必须一个一个传。
* 返回字段：`date/clickDate, cost, clicks, impressions, CTR, CPC, CPM, totalOrderCnt,
  totalOrderSum, totalOrderCVS, totalOrderROI`（小时粒度另有 `totalPayOrder* / totalDealOrder*`）。
* 取数上限：实测 30 天日粒度一次拿全，未遇到 +30 天截断。

## 4. 与现有按天库的关系

`dailystore` 的 `jzt_campaign` **已经**有「按计划 · 按天」的
`impressions / clicks / cost / totalOrderCnt / totalOrderSum / totalCartCnt`。

所以：

* **日粒度趋势 = 重复数据**，本地自算即可，不需要这个接口。
* **分时（小时）粒度 = 目前库里完全没有的新数据**（`KINDS` 里没有任何小时级 kind）。

→ 这个接口唯一值得抓的就是 `granularity:4`。

## 6. 可落地的动作

1. **分时折扣（推荐先做）**：对 04:00–05:00、23:00 设 30%–50% 折扣或直接关停；
   18:00–22:00 提价 10%–20%。以 10-11 为例，05:00 花 ¥96 只回 ¥47，压掉一半即可回血约 ¥48/天。
2. **按计划做「时段差异」而非「整体关停」**：如「佛手柑」全天 ROI 2.59 看似还行，
   但 12:00 单时段 ROI 0.62、花 ¥72 —— 只需给这个计划的 12:00 打折，不必动它其它时段。
3. **反哺关键词层**：把「同一关键词在不同时段的 ROI」和现有词分层（good/waste/low）交叉，
   可以识别「只在某几个时段有效的词」——这类词现在被整体判定为 waste 而被误否。

## 7. 口径注意（避免误判）

* ROI 按**点击发生的小时**归因（`clickOrOrderDay=15`）。所以 23:00 点击的订单只积累了约
  18 小时归因窗口，00:00 的有 24 小时以上 → **越晚的时段 ROI 天然偏低一点**。
  建议：只对**T-2 及更早**的日期做分时判定，或用 3–7 天分时均值再下结论，别拿今天的数据调价。
* 「关停某时段」会同时减少该时段的曝光与拉新，对新客占比高的类目要留出测试预算。
* 小时粒度不能跨天，别用 30 天区间去请求 `granularity:4`（会静默降级成按天）。

## 8. 复现脚本

| 脚本 | 作用 |
|---|---|
| `jd_roi/probe_trend.py` | 打开列表页、抓 DOM 与全量 XHR（定位接口用） |
| `jd_roi/probe_trend2.py` | 精准点「趋势」，拿到 `material/trendchart` 及其参数 |
| `jd_roi/probe_trend3.py` | 摸清 `granularity` 语义与区间边界 |
| `jd_roi/probe_trend4.py` | 账号级分时 + 「问题时段」清单 |
| `jd_roi/probe_trend5.py` | 按计划分时 + 逐计划「问题时段」 |

运行：`.venv\Scripts\python.exe -m jd_roi.probe_trend5 --account=main --day=2026-10-11`
