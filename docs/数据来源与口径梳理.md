# 京东广告运营分析 · 数据来源与口径梳理

> 目的：把「报表里每一个数字到底从哪个平台、哪个接口、哪一级口径来」彻底理清，
> 方便排查「为什么有些数看起来不对」，以及后续如果要对数、修数该去哪里改。
> 本文基于当前代码（`jd_roi/*`、v3 常驻服务）审计整理，2026-10-08。

---

## 0. 一句话总览

```
登录(京麦扫码) → 每天定时抓取 → 按天入库(data/daily/账号/日期/*.json.gz)
→ 选区间从本地聚合三期(前两期/前一期/所选区间)
→ 分析(analyze2) + 渲染报表(report2) + 回填Excel(fill_excel)
```

报表里的数据只有 3 个去处：**京准通（广告口径）**、**商智（店铺/经营口径）**、**ERP + Excel（成本口径）**。
没有别的数据源。

## 2. 数据流水线（项目如何运作）

### 2.1 按天抓取 → 按天入库（v3 常驻服务）

- **入口**：`webapp.py` 内 APScheduler 每天 **0:05**（`JD_SCHEDULE_HOUR/MINUTE`，Asia/Shanghai）触发 `scrape_day.scrape()`；
- **回刷**：京准通是「点击后 15 天归因」→ 每晚**重抓最近 15 天**（`JD_REFRESH_DAYS`），覆盖写入修正昨天的数据；商智当天结算后不再变。
- **落盘**：`data/daily/<账号>/<YYYY-MM-DD>/<kind>.json.gz`，8 类 kind：

| kind | 含义 | 说明 |
|---|---|---|
| `jzt_campaign` | 京准通概览-计划 | 含 `spuId`、`campaignType`，**包含全站智能推广(153)** |
| `jst_campaign` | 智能投放-计划 | 不含 153 |
| `jst_sku` | 智能投放-商品 | 含 `skuId`，与商智 `sku_id` 精确关联的主键 |
| `jst_searchword` | 智能投放-搜索词 | 按计划名聚合（接口不返回 campaignId） |
| `kw` | 快车-关键词 | 按 campaignId+keywordName |
| `sz_product` | 商智-商品明细 | 店铺级经营数据 |
| `sz_flow` | 商智-流量概况 | 店铺访客/浏览 |
| `oplog` | 京准通操作日志 | 人工调整记录 |

- **两个账号（店铺）**：`config/accounts.json` 配 main（主账号）/ b（账号B），各自独立 Profile 扫码。广告数据跨账号按 **skuId 累加**；商智按店铺分别保留（`shops` 字段）。

### 2.2 任意区间聚合（选区间 → 只读本地）

- 用户选 `[start,end]` → `analyze2.windows_for()` 自动生成 **三期**（w0 前两期 / w1 前一期 / w2 所选区间），各期等长。
- `dailystore.load_window()` 把区间内每天的 gzip 文件按 `AGG` 规则（按 key 合并且字段求和）聚合成「等同一次区间抓取」的结果 → **纯本地计算，秒级返回，不受接口限流影响**。
- 缺失的日期**按 0 计入**并提示「数据不完整」。

### 2.3 分析 + 渲染（`analyze2` → `report2`）

- `analyze2.build(start,end)`：账号总额、计划类型拆分（智能化 61 / 快车-关键词 2 / 全站智能 153）、按 SKU 交叉（广告=两账号累加 vs 商智=分店）、成本与保本线、词分层、调整复盘 → `d["advice"]/d["accounts"]/d["skus"]/d["plans"]/d["words"]/d["adjustments"]`。
- `report2.render()` 渲染 6 个 tab：①总结 ②商品ROI ③调整复盘 ④计划明细 ⑤搜索词诊断 ⑥行动清单，自包含 HTML（内联 ECharts，离线可看）。

## 3. 报表每个数字的出处（口径映射）

### 3.1 总结页（①）
| 指标 | 真实来源 | 关键点 |
|---|---|---|
| 广告花费 / 广告成交额 / ROI | **京准通概览** `jzt_campaign`（计划行求和） | 缺概览时**退化为智能投放口径**（`account_totals`，source 标「智能投放(概览缺失)」），此时**不含全站智能推广**，总额会偏小 → 报表会提示「口径降级」 |
| 店铺总成交（商智）/ 广告贡献 | **商智商品明细** `sz_product` 的 `$summary` 合计行（无则按 SKU 加总） | 广告贡献 = 广告成交 ÷ 商智成交；**>110% 置为不可比** |
| 店铺访客/浏览量/转化率 | **商智流量概况** `sz_flow`（`core`） | |
| 人工调整 / 系统自动改预算 / 正确与有问题 | **操作日志** `oplog` 解析 | 人工 vs 系统自动（kind=autoBudget）|
| 广告订单 / CPA / CPC / 点击 | 京准通概览 | 由花费/订单/点击派生 |

### 3.2 商品ROI页（②）—— 用户最常核对的一页
| 字段 | 来源 |
|---|---|
| 每个 SKU 的广告花费/成交/ROI | `jst_sku`（智能投放-商品，含 skuId，两账号累加）+ **全站智能推广从 `jzt_campaign` 按 `spuId` 补录**（否则漏主账号约 40% 花费） |
| 商智成交/访客/件数/订单（szAmt/szVisitors/szQty/szOrders） | `sz_product`（按 `sku_id`） |
| 广告渗透率 adShare | 广告成交 ÷ 商智成交（跨期归因时 >110% 显示为不可比） |
| 前台件单价（frontPrice） | **商智成交额 ÷ 件数**（消费者实付；ERP 的 `price` 恒为 null 不能用） |
| 到手结算价 supply / 单件贡献 / 保本 ROI | **ERP 接口** `settings.load_costs()`（按 skuId）|
| 毛利率 / 保本线 | 公式：贡献 = supply − 货款 − 运费 − 包材 − 人工；毛利率 = 贡献 ÷ 前台件单价；保本 = 1/毛利率 |
| 全店保本线（未命中 ERP 的 SKU 标 `*`） | `config/costs.json` → Excel「计算公式」全店口径 → 内置示例（客单价100/成本70/运费5 → 毛利率25% → 4.00） |
| 净利预估/毛利 | 商智成交(或广告成交兜底) × 毛利率 − 广告花费 |
| 高成交未投广告商品（机会清单） | 商智 w2/w1 有成交但不在广告 ids 中的 SKU |

### 3.3 调整复盘（③）
- 操作日志里每条**人工**调整 → 对齐该计划日粒度（`jst_campaign` isDaily=true）**调整前 7 天 vs 后 7 天**；无日数据退化为周窗口 w0→w1/w1→w2。
- 判定：正确/有问题/效果不明显/存疑/已止损/观察中/无基线/无法评估；**无基线不判定**（新建计划、长期暂停不算提效）。

### 3.4 计划明细（④）/ 搜索词诊断（⑤）/ 行动清单（⑥）
- 计划：`jzt_campaign`（含 153）+ `jst_campaign`；保本线 = 计划内各 SKU **按成交额加权**毛利率的倒数。
- 搜索词：`jst_searchword`（`searchTerm`，**按花费降序只取前 2000 行**）+ `kw`（`keywordName`）。
- 行动清单：基于词分层（高效=订单≥2 且 ROI>保本；废词=花费≥3 且 0 单；低效=花费≥10 且 ROI<保本）+ 定档规则（ROI≥放量线→放大；保本~放量→优化；<保本→止损）。

## 4. 关键口径（为什么两个平台数字天然对不上）

1. **归因窗口不同**：京准通所有接口统一 `clickOrOrderDay=15`（**点击后 15 天内成交**）`clickOrOrderCaliber=0`（成交订单）；商智是**当天成交快照**。→ 广告成交 > 店铺成交（渗透率 >100%）多半是归因跨期，属正常，报表标为不可比。
2. **下单 vs 成交**：概览与智能投放报表订单口径可能不同，同一分析内必须保持一致（代码里 `orderStatusCategory` 有差异之处已注明）。
3. **商智只到「昨天」**：`endDate >= 今天` 返回空数组**且不报错**（`code:0`）。正常分析窗口必须 ≤ 昨天。
4. **商智是店铺级**：每个店铺独立商智；跨店铺投同一 SKU 时，商智成交×店分别保留、广告跨店累加。
5. **商智件数口径**：ERP `_qty` 统计范围比京东大（含其他渠道/赠品），实测按 **1:1** 换算才自洽（换算后到手结算价会高于消费者实付，不可能成立）。
6. **前台件单价 ≠ 到手结算价**：ROI 分子是前台成交额（实测广告客单价÷商智客单价≈1.05），**保本线必须除以前台件单价**；扣除点后到手结算价口径的线会低 15~30%，把亏的判成赚。报表两种口径都给、判定只用前者。

## 5. 「数据不信任」的高危点自查清单

如果你觉得某几个数不对，按这张表逐项排查：

| 现象 | 最可能原因 | 在哪看 / 怎么修 |
|---|---|---|
| 总额比京东后台少 | ① 缺概览数据退化为智能投放口径（不含153）② 该区间有日期没入库（按 0 计） | 报表顶部「口径降级」「数据不完整」提示；控制台补抓 |
| 商智某些天全空 | 窗口含今天/明天（商智只到昨天） | 区间选到昨天为止 |
| 广告渗透率 >100% | 归因跨期（15 天窗口 vs 当天成交），可接受 | 报表已标不可比，不算错 |
| 保本线全店统一 4.00 | ERP 没连上 / Token 失效 → 退回 Excel 全店口径 | 总结页「成本来源」面板；检查 `.env` 的 `JD_COSTS_URL/TOKEN` |
| 搜索词缺低花费词 | 按花费降序截断前 2000 行（覆盖 ~99.9% 花费） | `JD_SW_MAX_ROWS` 调大 |
| 操作日志缺 8 月之前 | 接口静默截断，跨度大只返回前段 | `scrape_oplog sweep` 按 7 天分段已处理 |
| 昨天数据今天变 | **京准通 15 天归因，数据后面会长**，每晚回刷 15 天 | 属正常，隔天再看 |
| SKU 商品名带乱码/`&amp;` | 接口返回 HTML 实体未转义 | 报表渲染已 `html.unescape` |
| 某 SKU 到手结算价 ≥ 前台件单价 | 促销价/期间口径不一致，或 ERP 混入其他规格 | 报表标「成本口径待确认」 |
| 日数据/report_*.html 是旧报告 | **`ad_roi_report_v2.html` 生成于 10-06，早于 ERP 成本接入(10-07)**，保本线与当前口径不一致 | 以 `data/report_*.html` 或网页 `/report` 为准，重新 generate |

**最重要的一条**：`data/` 根下的 `ad_roi_report_v2.html` 是 10 月 6 日生成的**旧版报表**（当时还没接 ERP、保本线是全店示例口径 4.00）；10 月 7 日才完成 ERP 逐 SKU 成本接入。**看报表请用网页 `/report` 或 `data/report_*.html`，并确认总结页成本来源 = 「供货方接口 / 本地缓存」**，否则看到的保本线不是真实成本算的。

## 6. 常用命令 / 接口自查

```bash
# 服务
uvicorn jd_roi.webapp:app --host 0.0.0.0 --port 8000      # 网页 /report 选区间
# 任意区间重新分析（网页等价操作）
python -m jd_roi.analyze2 --start 2026-09-27 --end 2026-10-03
python -m jd_roi.report2  --start 2026-09-27 --end 2026-10-03
# 手动补数据
python -m jd_roi.scrape_day 2026-09-27 2026-10-03
python -m jd_roi.scrape_day --account=b --force 2026-10-03 2026-10-03
# 当前成本口径
python -c "import os; from jd_roi import settings; print(settings.COSTS_SOURCE)"
```

> 环境变量：`JD_COSTS_URL` / `JD_COSTS_TOKEN` 在 `.env`（不入库）；`JD_DATA_DIR/JD_AUTH_DIR/JD_CONFIG_DIR` 默认 `data/ auth/ config/`。
